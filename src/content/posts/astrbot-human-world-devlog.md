> 项目：`astrbot_plugin_human_world` · 当前本地版本：0.7.3  
> 本文记录截至 2026 年 10 月 26 日的实现，不是公开发布公告或一键安装教程。

给 QQ 机器人写人格时，我逐渐遇到了一个问题：提示词能规定它怎么说话，却很难解释它为什么会形成某种看法。

我希望机器人接触一段内容之后，可以留下自己的理解，在之后的聊天里有所体现。但如果让模型看完材料就直接改写人格，又很容易把误解、猜测甚至编造的经历一起保存下来。

因此，我为 AstrBot 制作了「人间札记」：一个把视频材料、学习反思、人工审核和后续聊天连接起来的插件。它把一次学习拆成可以查看、核对、批准和撤回的记录，让“成长”有来源，也留得下修改的余地。

## 从一段视频，到一条可使用的认识

插件的主要流程是：

```text
添加视频或收集推荐
        ↓
读取实际可用的文字、声音与画面
        ↓
整理来源，逐页交给模型理解
        ↓
生成成长信笺
        ↓
人工核对，选择人格摘句
        ↓
批准、同步并核验记忆
        ↓
在同一人格的后续聊天中补充这些认识
```

这里的“学习”指的是读取材料、生成反思和保存外部记忆。它不会训练模型权重，也不会让模型永久获得某种新能力。

## 工作台：待学习、成长信笺与人格摘句

我把日常操作放进 AstrBot 的可视化工作台，分成三个部分。

**待学习**用来添加视频链接、查看队列和启动任务，也可以在启用推荐收集后接收待选材料。

**成长信笺**保存一次学习的完整过程，包括来源、实际取得的材料和模型的理解。信笺保留八个字段：遇见、事实、作者观点、推测、先前判断、认识修正、缺失信息、下一次回应。

这些字段让审核者可以分别看清：视频里实际出现了什么，作者表达了什么，以及模型自己又推测了什么。

**人格摘句**则是从信笺中挑选值得带入后续聊天的一句话。每封信笺可以从“认识修正”或“下一次回应”中原样摘取一句，也可以什么都不选。摘句需经过审核批准，才能进入后续使用流程。

我希望机器人能有自己的理解，但是否值得长期保留，仍然需要有人把关。

## 为理解视频准备六路材料

只读标题和简介，很容易让机器人围绕标题猜内容。为此，插件在完整学习流程中整理六路材料：

| 材料 | 可以帮助理解什么 | 需要保留的边界 |
| --- | --- | --- |
| 投稿封面 | 作者如何呈现这段视频 | 封面不代表正片实际出现的画面 |
| 投稿简介 | 作者补充的背景与说明 | 投稿者说明仍需与实际内容区分 |
| 平台字幕 | 视频提供的语言内容 | 人工字幕、AI 字幕和未知类型分别标记 |
| 弹幕热区 | 观众集中讨论的时间段 | 当前快照和密度不能代表所有观众 |
| 热评 | 观众的部分解读与回应 | 点赞、置顶和评论本身不是事实证明 |
| 视频抽帧 | 取得的时间点上实际有什么画面 | 抽帧会漏掉短暂或连续发生的事件 |

没有平台字幕时，插件还可以使用本地音轨转写，并对已取得的抽帧做字幕 OCR。平台文字、AI 转写、OCR 和视觉描述分别保留来源，避免混成一份看似准确的“原文”。

音轨转写使用 faster-whisper，画面字幕识别使用 rapidocr-onnxruntime。视觉解释则交给配置的图片理解模型。

这套流程仍然存在采样和下载保护，并不是完整、连续地看完每一帧。歌声、专名、配乐和复杂画面都可能造成误识别，工作台保留原图、文字来源及可用音轨，供审核时核对。

## 引用由程序取出，理解由模型表达

我比较在意的一点，是不要让模型把自己的改写伪装成原文。

在信笺生成过程中，模型选择程序提供的来源标识，再由程序取出对应原文。这样可以减少模型重新誊写时漏字、改标点，或将解释混进引句的问题。

与此同时，插件尽量保留实际取得的材料和处理进度。缺少字幕就标记字幕缺失，无法判断作者观点就保持未知。模型可以提出解释，但解释需要带着它的来源和不确定性。

## 人格怎样发生变化

批准一条摘句后，插件会将它同步到配置好的 Memory MCP，回读核验，再写入对应人格的摘句文件。同步失败时保持待同步状态，不把它显示成已经生效。

后续聊天时，插件为同一人格补充最近七条已批准、核验通过的摘句，同时保留来源和适用范围。这个过程不覆盖 AstrBot 中保存的基础人格正文。

因此，当前的变化发生在模型请求中的补充上下文：机器人在回复前能够参考这些认识。是否真正体现在某一次回应里，仍然取决于模型，不能仅凭“已加载”就宣称它已经形成了稳定性格。

完整记录保存在本地数据库和审核界面中；原项目格式的 Markdown 导出保留最近 128 条，避免导出无限增长。历史记录保存多少，与一次聊天实际加载多少，是分别处理的。

## 多个人格各自拥有学习记录

工作台顶部可以选择“学习给谁”。选择的人格决定之后新任务的归属，以及当前显示的队列、信笺和摘句。

切换不会把旧记录搬给另一个人格，也不会自动批准新记忆，更不会替换 QQ 或 WebChat 会话当前使用的人格、模型。同一段视频可以分别交给不同人格学习，形成各自的记录。

这里按人格组织学习，不等于已经实现所有用户按 QQ 号自动归档、跨群接续话题。Memory MCP 也不会自动替插件完成所有访问范围和隔离逻辑。

## 群里发视频，可以只聊天

除了完整学习，我还加入了普通视频聊天路径。

群友发送 B 站链接后，插件会尝试取得可用文字、音轨和关键帧，将这些材料交给当前人格，让它根据实际内容接话。这条路径与学习审批分开：分享视频不意味着自动把视频写成长期记忆。

这也是我比较想保留的使用体验：有时只是想让机器人陪着看一段视频，聊聊感受，没有必要每次都变成一堂“学习课”。

如果实际只取得标题，或视频读取失败，机器人应当说明缺失；不能根据标题猜一段内容，再说自己已经看过。

当前版本还包含纯 @ 消息的辅助处理，让没有正文、只有真实机器人 @ 的消息能够进入简短招呼流程。这是聊天接入上的补充，与视频学习和记忆审核分开。

## 记错之后，也应当能撤回

外部记忆总会出现不合适、过时或理解错误的内容，所以删除和停用也是这个插件的一部分。

删除一份关联的成长记录时，插件会处理对应信笺、摘句及自己的 Memory MCP 节点。远端暂时不可用时，先停止新聊天继续引用，保留待完成的撤回任务，供后续重试。

删除不代表抹去一切痕迹：旧聊天上下文、手动备份、模型已经接收的请求，以及可能被其他记录复用的媒体缓存，不会因此全部消失。停用整个插件也不等于自动删除已经同步的远端记忆。

人间札记并非从零实现了全部视频读取能力。内置读取器复用了 [dsh-bili-humanism](https://github.com/InariNGT-Ofiicial/dsh-bili-humanism) 的部分代码，基线提交为：

复用部分包括读取服务、文字分页、信笺格式校验、账本导出及人格文件处理，保留原项目的 MIT 许可和署名。

我在此基础上完成了 AstrBot 插件适配、可视化工作台、学习队列与审核管理、多路视频材料整理、本地转写与 OCR 接入、Memory MCP 同步，以及后续聊天的上下文补充。普通视频聊天和纯 @ 辅助也整合在当前插件中。

本地适配修改了学习数量策略，并调整了媒体备用地址选择等行为，所以不能将内置代码简单描述为“完全未经修改的上游原版”。这也是 AstrBot 适配项目，不代表原项目官方发布。

## 运行条件与当前边界

本地使用环境为 AstrBot 4.29.1，插件元数据声明版本条件为 `>4.26.0`；这个声明不等于所有更高版本都已完成兼容验证。

主要依赖包括 Node.js、媒体处理 Python 环境、av、Pillow、faster-whisper、rapidocr-onnxruntime，以及配置好的模型服务。需要记忆同步时，还要准备 Memory MCP。部分视频读取需要有效的 B 站登录凭据。

插件仍受这些实际条件影响：

- 内容能否取得，取决于平台可访问性、凭据和当前接口状态。
- 画面解释、转写与反思可能出错，需要人工核对。
- 当前没有自动改写基础人格正文，也没有保证长期人格变化的机制。
- 没有接入视频角色的通用反向图片搜索；检索候选不能直接当成识别结论。
- 登录异常或平台限制会触发暂停保护，需要检查原因后处理。

API Key、Cookie、SESSDATA、私人账本和聊天记录都应与插件源码分开保存，不能随博客附件公开。

## 我希望留下的是一段可以回看的成长过程

人间札记目前最重要的成果，是把“看过什么、怎样理解、批准了什么、后来使用了什么”连接成了一条能够回看的过程。

我想继续观察的，是这些有来源的认识能否在日常聊天里慢慢形成连贯的表达，同时仍然允许修正和遗忘。对一个长期陪伴群聊的机器人来说，这种可核对、可修改的积累，是我愿意继续做下去的方向。
